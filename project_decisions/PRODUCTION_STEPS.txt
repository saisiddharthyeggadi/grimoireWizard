PHASE 1: AUTH AND PER-USER ISOLATION   (highest priority)
---------------------------------------------------------
Code implementation is prepared: Angular Google sign-in, Bearer-token
validation, AUTH_MODE enforcement, per-user document IDs, and the RLS/storage
migration. These checklist items remain open until the migration is applied
and verified in staging; do not ingest real data before that verification.
[O] Enable the Google provider in Supabase Auth.
[O] Set the Google OAuth consent screen to "In production"
    (basic scopes only: openid, email, profile).
[O] Frontend signs in with Google and sends the JWT as
    "Authorization: Bearer".
[O] FastAPI verifies the JWT on every request except GET /health.
[O] Add a profiles table with role: user or admin. No other roles.
[O] Add AUTH_MODE=off|on. With off, treat every request as one fixed
    dev user. The backend must refuse to start with AUTH_MODE=off when
    ENV=production.
[O] Add a documents table (id, user_id, sha256, filename, storage_path,
    status, error, page_count, created_at).
[O] FIX BEFORE INGESTING REAL DATA: derive the document ID from
    user_id + sha256, with a unique constraint on (user_id, sha256).
    Today the ID comes from the hash alone, so two users uploading the
    same PDF would collide and one could learn the other has that file.
[O] Add user_id to conversations and document_chunks.
[O] Enable RLS on every table, with policies tied to user_id.
[O] Backend queries Supabase as the user (their JWT) so RLS applies.
    Vector search becomes an RPC function that respects RLS. The
    service-role key is used only for background ingestion.
[O] Store PDFs in Supabase Storage under a user_id path prefix, with
    storage policies.
Done when: an automated test proves user A cannot read user B's
documents, chunks, conversations, messages, or PDF files.


PHASE 2: ENVIRONMENTS, SECRETS, CI/CD
-------------------------------------
[ ] Create two Supabase projects: staging and production.
[ ] Create two Cloud Run services: staging and production, running the
    same Docker image (promote the image, do not rebuild).
[ ] Set Cloud Run minimum instances to 1, so the embedding model (and
    reranker, if local) is already loaded. Scale-to-zero cold starts
    would slow the first question.
[ ] Check the Cloud Run CPU setting for background work after a
    response ends (see current Cloud Run docs), or move ingestion to a
    Cloud Run Job.
[ ] Put the service-role key and the Gemini key in Google Secret
    Manager. Separate keys per environment. Plan for rotation.
[ ] Keep .env gitignored. The browser app only ever gets the public
    Supabase URL and anon key.
[ ] GitHub Actions pipeline: lint -> tests -> build image -> deploy to
    staging -> manual approval -> promote to production.
[ ] Apply migrations with the Supabase CLI in CI, staging first.
[ ] Deploy the Angular build to the static host, with per-environment
    config (API URL, Supabase URL, anon key).
[ ] Register separate Google OAuth redirect URIs per environment.
[ ] CORS: allow only the known frontend origins (env var such as
    CORS_ORIGINS). Never "*" in production.
[ ] Write down the rollback step: redeploy the previous image and the
    previous Angular build.
Done when: a merge to main reaches staging automatically, and a manual
approval promotes the same image to production.


PHASE 3: ABUSE AND COST PROTECTION
----------------------------------
[ ] Per-user rate limits in the API (slowapi, with a shared store if
    you run more than one instance).
[ ] Quotas: max PDF size, max pages, documents per user, messages per
    day, concurrent ingestions, request timeouts.
[ ] Validate uploads: file type, size, and that the file really is a
    PDF. Reject scanned/image-only PDFs with an unsupported_pdf error.
[ ] Gemini calls: timeouts, retries with backoff, and a clear
    llm_unavailable error when it is down.
[ ] Set a hard spend cap or budget alert at the LLM provider.
[ ] Put Cloudflare (WAF, rate limits) in front if the app is public.
[ ] If you launch invite-only, enforce the email allowlist.
Done when: a script that spams uploads or questions is throttled, and a
budget alert fires in a test.


PHASE 4: OBSERVABILITY AND ALERTING
-----------------------------------
[ ] Structured JSON logs with a request ID on every line, shipped to
    Cloud Logging. Do not log PDF contents or full prompts.
[ ] Sentry on the backend (and the Angular app) for errors.
[ ] Record per-stage latency: rewrite, retrieval, rerank,
    time-to-first-token, total.
[ ] Record token usage and cost per request.
[ ] LLM tracing with Langfuse or Pydantic Logfire (your pick).
[ ] Uptime check on GET /health.
[ ] Alerts on: error rate, p95 latency, daily LLM spend, ingestion
    failures.
Done when: you can take one slow request ID and see which stage was
slow, and a forced error produces an alert.


PHASE 5: INGESTION ROBUSTNESS
-----------------------------
[ ] POST /documents returns immediately; ingestion runs in the
    background (Cloud Run Job or a small queue).
[ ] Document status: processing, ready, failed (with an error message).
[ ] Retries for failed ingestion, and cleanup of partial results.
[ ] Keep stale-trailing-chunk cleanup on re-ingest.
[ ] Store the original PDF and expose a signed URL
    (GET /documents/{id}/file) for the viewer.
[ ] Capture bounding boxes per chunk (bboxes) for citation highlights.
[ ] Check chunk size against the embedding model's input limit (about
    256 word pieces for all-MiniLM-L6-v2) so text is not silently cut.
Done when: a large PDF uploads without blocking, shows progress, and a
deliberately corrupted PDF fails cleanly with a clear message.


PHASE 6: TESTING
----------------
[ ] Unit tests for chunking, parsing, and request validation.
[ ] Integration tests against real Postgres + pgvector (local Supabase
    or the staging project).
[ ] Auth in tests: create test users with the Supabase admin API and
    mint their sessions. Do not automate the Google login screen.
[ ] Mock the LLM in most tests; keep a few real-call smoke tests.
[ ] Playwright end-to-end test of the Angular flow: sign in, upload,
    attach, ask, see streamed answer, open a citation.
[ ] Mandatory isolation test (see Phase 1).
[ ] Contract test for the endpoints Streamlit uses, so backend changes
    cannot break it silently.
[ ] Test that streaming works through your host and any CDN/WAF
    (no buffering, no early timeouts).
[ ] Simple load test: several users asking questions at once, watch
    latency and memory.
[ ] RAG evaluation set (15-20 Q/A, including questions NOT answered in
    the documents). Re-run before every release.
Done when: CI runs all of the above (except the real-call smoke tests,
which can run nightly) and blocks a release on failure.
